# تقرير تسليم النسخة المصدرية — إصلاح الاستعادة والترخيص وتسجيل الدخول

**Build ID:** `FINAL-RESTORE-20260813`  
**تاريخ المراجعة:** 2026-08-13  
**النسخة:** `2.0.1`  
**الحكم الصادق:** الإصلاحات المصدرية واختبارات الاستعادة المركزة ناجحة، لكن هذه الحزمة ليست إعلان اعتماد Production نهائي؛ اختبار EXE مبني ومثبت من هذه الحالة نفسها ما زال `UNVERIFIED`، كما أن قرار الإبقاء على مولد تراخيص V5 داخل برنامج العميل يُبقي `AUD-LIC-002` و`AUD-LIC-004` مفتوحين.

## 1. العطل الذي تم إصلاحه

تم تتبع الخطأ الظاهر للمستخدم:

`An object could not be cloned · RST-*`

إلى تمرير `Promise` راجعة من `getBackupV2Password()` عبر `contextBridge` بدل انتظار قيمتها. تم إصلاح كل مسارات الاستعادة والنسخ الاحتياطي التي كانت تكرر الخطأ، وإضافة مسار Main موثوق لاستخدام سر Backup V2 المحفوظ في `safeStorage` أثناء الإعداد.

## 2. الإصلاحات المنفذة

1. **Backup V2 والاستعادة:** انتظار كلمة مرور النسخة قبل IPC، دعم كلمة مرور `safeStorage` من Main، وعدم استبدال القاعدة قبل فك التشفير والتحقق من SQLite.
2. **الاستعادة أثناء الإعداد:** قبول قاعدة SQLite التي تحتوي فقط على صفوف الإعداد/الجهاز، مع رفض الاستبدال إذا كانت القاعدة تحتوي بيانات تشغيلية حقيقية.
3. **النسخ القديمة V3:** ترحيل النسخة القديمة إلى قاعدة مرحلية ثم فحصها واستبدالها ذريًا؛ كلمة المرور الخاطئة لا تغيّر القاعدة المحلية.
4. **هوية Device B:** استعادة بيانات العمل مع الاحتفاظ بترخيص وهوية وربط فرع الجهاز الجديد بدل وراثة UUID/فرع الجهاز المصدر.
5. **اختيار نسخة Drive:** عرض حتى عشر نقاط استعادة، وعدم افتراض أن أحدث ملف هو الصحيح إذا وُجدت عدة نسخ.
6. **تسجيل الدخول بعد الاستعادة:** الاعتماد على مصادقة Main؛ لم يعد Renderer يرفض كلمة المرور لعدم امتلاكه hash محميًا.
7. **الترخيص بعد إعادة التشغيل:** قراءة الترخيص أولًا من SQLite باعتباره المصدر الموثوق، ثم استخدام المرايا القديمة كمسار توافق فقط.
8. **المزامنة الأولية:** بعد استعادة SQLite كاملة لا يتم تشغيل hydrate قديم يتوقع ملفات config اختيارية غير موجودة؛ يتم سحب سجل العمليات ثم تثبيت اكتمال bootstrap.
9. **منع الاستعادة المضللة:** نسخة checkpoint أو نسخة ناقصة لا تُعرض باعتبارها استعادة قاعدة كاملة مؤكدة.
10. **الواجهات المرتبطة:** قائمة نقاط الاستعادة تستخدم DOM آمنًا و`textContent` وتحافظ على شكل UI الحالي.

## 4. دليل الاختبار

### الاختبارات المركزة

نجحت 13 مجموعة اختبار مرتبطة مباشرة بالحادث والمسارات المتأثرة، وتشمل:

- Backup V2 من SQLite إعداد فعلي، والتحقق من `quick_check`.
- منع التعديل عند كلمة مرور خاطئة.
- استعادة V3 قديمة إلى staging ثم atomic swap.
- استعادة مستخدمين متعددين والتحقق من كلمتي المرور.
- الاحتفاظ بترخيص الجهاز الجديد وربط فرعه وهويته.
- تسجيل دخول Main من بيانات مستعادة دون كشف password hash للـRenderer.
- بقاء الترخيص بعد إعادة التشغيل.
- OAuth state، اكتشاف Drive، وsetup-state sync authorization.
- مولد تراخيص V5 الحالي: 441 تركيبة اجتازت اختبار التوليد/التحقق الوظيفي.

### فحص Drive الحقيقي دون تعديل بيانات المستخدم

تم تشغيل تشخيص read-only ثم استعادة على profile مؤقت معزول:

- الاتصال بـGoogle Drive نجح.
- تنزيل أحدث Backup V2 الحقيقي نجح.
- فك التشفير والاستعادة كانا cloneable.
- SQLite `quick_check = ok`.
- إعادة الفتح وpre-auth نجحا.
- الترخيص بقي موجودًا بعد إعادة التشغيل.
- بيانات المستخدم الحقيقية لم تُستبدل ولم تُحذف.

## 5. تفسير حالات الاختبار الست غير الناجحة

1. `p0-e:licensing-production`: يفشل عمدًا لأن حزمة العميل ما زالت تحتوي مولد/سر توقيع V5 بناءً على قرار مالك المنتج بإرجاع التوليد كما كان.
2. `license:test`: الأسباب نفسها، وتحديدًا وجود `TADAWI_OFFLINE_LIC_V4` و`LIC_SECRETS` ومسارات HMAC في المصدر المعبأ.
3. `v2-5.7:production-release`: بوابة تاريخية تعتمد على lifecycle/artifact إصدار سابق، وليست دليلًا على فشل مسار الاستعادة الحالي.
4. `v2-5.7:scenarios`: سيناريو واحد من ثمانية يفشل بسبب بوابة الإصدار السابقة.
5. `v2-5.7:windows-uat-runtime`: يشير إلى EXE قديم في `dist` ذي SHA-256 سابق؛ لم يُبن EXE جديد ضمن هذا التسليم.
6. `v2-3.5:verify-uninstall-prep`: وجد profile المستخدم الحقيقي في `%APPDATA%\Cupping Center`. لم يتم حذفه لأن ذلك إجراء مدمر خارج اختبار معزول.

## 6. الحالة الفعلية للنسخ الموجودة على Drive

الجرد الحقيقي وجد أن **أحدث** Backup V2 صالح تقنيًا لكنه صغير ويحتوي مستخدمًا واحدًا من نوع Owner ولا يحتوي عملاء أو موظفين أو زيارات. لذلك ظهور Owner فقط لم يكن بسبب إخفاء سجلات داخل هذا الملف؛ الملف نفسه sparse.

توجد نسخ أقدم بحجم يقارب 1.72 MB بصيغة V3 المشفرة. استعادتها أصبحت مدعومة ذريًا، لكنها تحتاج **كلمة مرور النسخ الاحتياطي التاريخية الصحيحة**. لا يمكن تجاوز تشفير هذه النسخ أو استنتاج كلمة مرورها من المصدر.

تعليمات مهمة: لا تحذف النسخ القديمة من Drive، واخترها يدويًا من قائمة نقاط الاستعادة بعد بناء النسخة الجديدة.

## 7. المشاكل الحالية المفتوحة

### Critical / Release blocker

- `AUD-LIC-002`: سر توقيع V5 موجود داخل حزمة العميل ويمكن استخراجه نظريًا وتزوير ترخيص. هذا تعارض أمني مباشر مع Baseline التجاري، رغم أن التوليد يعمل وظيفيًا.
- لا يوجد اختبار EXE جديد مبني ومثبت من هذا المصدر؛ لذلك متطلبات `AUD-RST-007` إلى `AUD-RST-010` و`AUD-AUTH-006` و`AUD-LIC-014` تبقى `UNVERIFIED` وفق قاعدة التدقيق، وليست `PASS` نهائيًا.
- الاستعادة الفعلية لإحدى نسخ V3 الكبيرة لم تُنفذ لعدم توفر كلمة مرور النسخة التاريخية.

### High / Verification

- `AUD-LIC-004`: واجهة إنشاء التراخيص محمية بجلسة Developer صادرة من Main، لكن قدرة التوقيع نفسها ما زالت ضمن تطبيق العميل.
- `AUD-SEC-008` و`AUD-SEC-012` و`AUD-SEC-013`: منطق المصدر مغطى بالاختبارات، لكن دليل Installed EXE/بيئة Windows المطلوب في Baseline غير مكتمل.
- البرنامج/المثبت غير موقّع Authenticode ضمن هذا التسليم.

### بيانات وليست عيب كود

- أحدث نسخة Drive لا تحتوي بيانات النشاط المطلوبة. يجب اختيار نسخة أقدم وإدخال كلمة مرورها الصحيحة.
- لا يمكن ضمان استعادة بيانات غير موجودة داخل الملف المحدد.

## 9. خطوات Cursor الإلزامية قبل اعتماد Production

1. فك حزمة المصدر في مسار جديد وعدم نسخ `dist` أو profile مستخدم قديم فوقها.
2. تشغيل `npm ci` ثم `npm run lint` ثم `npm test` وتسجيل أسباب الحالات الست بدل تغيير expected tests.
3. حسم قرار المنتج: نقل مولد V5 إلى أداة داخلية منفصلة وآمنة، أو قبول أن Baseline التجاري سيظل `NO-GO`. لا يمكن الجمع بين سر توقيع مضمّن داخل كل نسخة عميل وبين شرط منع تزوير الترخيص.
4. بناء `npm run build:prod`، وحساب SHA-256 للـEXE الناتج.
5. التثبيت على Windows profile نظيف واختبار: OAuth حساب صحيح/تبديل الحساب، اختيار نسخة Drive، V2، V3 بكلمة مرور صحيحة وخاطئة، restart، Owner/staff login، الترخيص، branch binding، وinitial sync.
6. اختبار Device A/B فعلي: تعديل متزامن، delete/update conflict، offline/reconnect، duplicate delivery، restart، وفشل publication/version.
7. عدم إعلان أي Finding `PASS` إلا بعد إرفاق دليل EXE المثبت في `AUDIT-TRACEABILITY.md`.

## 10. محتويات حزمة المصدر

الحزمة تتضمن المصدر والاختبارات والتوثيق وهذا التقرير. تستبعد عمدًا:

- `node_modules`
- `dist`
- `artifacts` القديمة
- `.codex-validation` وملفات التشخيص المحلية
- ملفات `.env` و`*.local.json`
- `license/data` و`pat-reports`
- بيانات `%APPDATA%` وأي profile للمستخدم

يتم توزيع SHA-256 بجوار ملف ZIP، لأن تضمين hash الأرشيف داخل الأرشيف نفسه غير ممكن دون تغيير الـhash.
